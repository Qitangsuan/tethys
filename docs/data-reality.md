# 数据现状与路线判断（2026-11-24）

> 触发：新规则集（`since=2026-11-21`，7 条）注入满 3 天后跑一轮 `collect → classify → verify → ready`，
> `ready.py` 报 GO，但 `verify.py` 四条可验证规则全判「样本不足」。查下去发现**不是规则没用，也不是方法坏了，
> 是样本在数学上攒不到**。本文把账摊开，并给三条出路。

## 2. 结论：靠自然使用攒样本，这条路走不通

`ready.py` 现在会直接算这笔：**按当前 21.3 调用/天，达 2,000 调用还需 ~91 天，达功效规划 13,075 调用还需 ~610 天。**

610 天是拿「11-21 之后三天 64 次调用」当速度算的，这三天本身偏低，换个更乐观的口径也一样救不回来：

- 就算速度翻 10 倍（213 调用/天），仍需 ~61 天/臂，且要求用户天天这个强度；
- 就算只检测 50% 降幅里最宽松的一档，样本量也只减半；
- 真正的问题不是「差 3 倍」（2026-11-20 的判断），而是**差 200 倍**——三天 64 次 vs 每臂 13,075 次。

**这不是方法失败，是测量对象频率太低。** 规则集注入 AGENTS 后，只有当 agent 真的去读规则、真的遇到对应失败场景，才能产生一次可比对的事件；用户不怎么用 DSH 的时候，这个分子分母一起躺平。

## 3. 三条出路（互不排斥，代价不同）

| 路线 | 做什么 | 代价 | 能得到什么 |
|---|---|---|---|
| **A 主动造样本** | 前瞻 A/B：每天固定跑 N 个任务，两臂（旧块/新块）对照；`experiment_switch.py` 已有开关能力 | 每臂 13,075 调用 ≈ 按现价几百元到上千元，外加每天几十分钟 | 唯一能回答「规则有没有用」的路；结论只对当时模型路由成立 |
| **B 判据下沉行为层** | 只验「规则被执行了吗」（`audit_behavior.py` 口径：read 前有没有先 glob、edit 失败后有没有重读），样本需求比「率下降」低一个量级 | 便宜，样本已经在攒 | 能出「行为改变了」的硬结论；**不能**推出「失败变少了」——规则 6 的现成反例：read 前 glob 从 2.6%→8.6%（3.3 倍），失败率没显著降 |
| **C 承认天花板，改投环境治理** | 审计已证：环境/工具类占真失败 67%，规则能管的约 18%；把力气投到填坑（Remote 未配置、qwen 嵌套参数、PS 5.1 BOM、子代理空转等） | 一次性投入，收益直接 | 真失败总量会降，但**不能归因给规则**；项目定位从「验证规则」变成「维护规则集 + 治环境」 |

**B 路线的补充实测**（同轮查的后臂 65 次调用构成）：`web_fetch` 32、`read` 11、`save_token_expand` 11、`pwsh` 8，
**`edit` 为 0**。也就是说现行 7 条规则里最干净的行为契约（R5「编辑失败后重读再改」）在后臂还没有可测样本——
行为层门槛确实低一个量级，但它同样要求「有人真的在干活」，不是随便调几次工具。R4 的 read 事件有 11 个，
但现行 R4 语义已从「read 前先 glob」改成「路径不确定才定位」，旧的正向检测不再是正向指标，需要重写检测口径。

**我的判断**：B 立即可做（零成本，下次判定就能出）；C 是真正有 ROI 的那条；A 只在用户明确愿意投钱投时间时才做——它也是上一轮框架挑战里 kimi 说的「第一个待检验对象」唯一能被检验的方式。

## 4. 本轮修掉的流水线问题（不修会持续误报）

| 问题 | 症状 | 修法 |
|---|---|---|
| `ready.py` 把「样本够验证」和「有事可做」混成一个 GO | 新失败族一出现就报 GO，诱导开一个必然样本不足的验证轮次 | 分三级输出：`VERDICT=verify`（样本够，可出判决）/ `work`（只可归因）/ `none`；返回码 0 仅对应 verify/work |
| 验证门槛用「上次判定以来的新增会话」 | 刚判完就归零，永远报不出真实差距；后臂到底攒了多少看不见 | 改按规则 `since` 分臂算后臂规模，直接跟 `minSessionsPerArm` 与功效规划比，并给出 ETA |
| 新失败族把「补采到的历史失败」当新事件 | 新解压旧会话会凭空触发 GO | `classify.py` 输出 `previousGeneratedAt`；`ready.py` 用样本发生时间过滤，全部早于上次判定的不算新族 |
| `REMOTE_DISCOVERY_FAILED` 未计入配置态 | Remote 面板未配置的 5 次失败污染真失败分子 | 加进 `caliber.configKinds`（`caliber-2026-11-24-1`），与「API credentials are not configured」同类 |
| `data/audit/` 里放文档 | 文档混在可重算目录里 | 框架挑战草稿移入 `docs/framework-challenge.md` |

回归测试：75 → **81 项**（新增 6 项覆盖后臂门槛、前后臂切分、新失败族时间证据）。

## 5. 下一步（按优先级）

1. **B 路线落地**：把行为层判据写进 `verify.py` 或独立 `audit` 报告，让它跟着每次判定跑——这是唯一现在就能出结论的判据。
2. **C 路线选 3 个坑填**：从真失败 Top 榜里挑（`exit_1_real` 80 / `edit_no_match` 42 / `web_fetch_fail` 33 / `file_read_missing` 26），逐个归因到根因，能修的修、能写进规则的写。
3. **A 路线等用户拍板**：愿意投预算就跑 `experiment_plan.py` 复算 → `experiment_switch.py` 开臂；不愿意就明确写「本项目不追求效果因果结论」。
4. 门槛修复后，每日 `ready_check.py` 会在桌面留 `潮汐-有事可做-YYYYMMDD.txt`，把「后臂 X 会话 / Y 调用，还差多久」直接写在脸上。
